# Working in Runveil

- Before changing code, inspect the repository state and the relevant charter, architecture, roadmap, ADRs, and existing implementation. Follow any narrower `AGENTS.md` for the files you touch.
- Follow the current user request first. For project guidance, `docs/PROJECT_PLAN.md` is the charter; accepted `docs/adr/` decisions and `ARCHITECTURE.md` govern technical boundaries; `ROADMAP.md` defines phase scope and review gates. Use `README.md`, `CONTRIBUTING.md`, CI, and configuration for current setup and checks. Treat handoffs as evidence of completed work, not new requirements. Surface conflicts or stale assumptions and use engineering judgment rather than copying a plan blindly.
- Implement only the current coherent, reviewable slice. Do not build later phases, speculative packages, or unused abstractions. Keep the core agent runtime owned by this project; use libraries for supporting concerns. Favor simple, testable behavior and verifiable engineering evidence over feature count or buzzwords.
- Favor minimal, high-value deterministic tests: a small number of behavioral, integration, and boundary tests for important, failure-prone logic. Avoid exhaustive or trivial tests, implementation-detail tests, coverage-percentage chasing, and tests added merely to increase test count. Keep Python and TypeScript strictly typed. Run applicable formatting, lint, type, test, build, and smoke checks described by CI and the README; report exactly what ran and any gaps. Keep manifests and lockfiles consistent when dependencies change.
- Preserve security boundaries: validate untrusted input, constrain tool and external side effects, and keep secrets, credentials, local `.env` files, and sensitive data out of source, logs, traces, and test fixtures. Keep live or paid provider tests opt-in.
- Update affected documentation when behavior or boundaries change. Record significant architectural decisions and trade-offs in an ADR; keep the charter, architecture, and roadmap accurate without duplicating them here.
- Do not commit or push unless explicitly instructed. At completion, hand off the implementation summary, files created and modified, key decisions, verification commands and results, remaining concerns, and the recommended next slice; then stop for review.
